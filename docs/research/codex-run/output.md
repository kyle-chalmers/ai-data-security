## 1. Threat-model framing and ranking

**Inference—ranked for data professionals connecting coding agents to warehouses:**

1. **Data-access boundary / blast radius.** Can the identity actually read raw data, write data, alter permissions, or reach ungoverned storage? This is the first priority because it is directly observable, deterministic to audit, and the thesis addresses it well.
2. **Lethal-trifecta exfiltration.** Does one agent combine private-data access, untrusted content, and an external communication channel? This is the highest-consequence composition risk. The thesis reduces one prerequisite—raw private-data access—but does not remove untrusted content or exfiltration capability.
3. **Agent configuration and MCP/skill supply chain.** Which instructions, server commands, OAuth scopes, environment variables, and silently changed skills shape what the agent can do? Current AC checks are the right seam, but they are intentionally shallow.
4. **Non-human identity lifecycle.** Is the agent credential dedicated, attributable, narrowly scoped, rotated, and offboarded? The thesis correctly prefers a dedicated identity, but it needs lifecycle evidence rather than only role naming.
5. **Basic data hygiene relabeled for AI.** Secrets in repositories, local transcripts, PII in files, and overly broad permissions remain material; AI makes their reach and speed worse but does not create the underlying control failures.

**Where the thesis fits.** It is the recommended architecture for framing 1 and a useful mitigation inside framing 2. Schema segregation and a separate identity constrain what can be exfiltrated; masking/hashing reduce raw-value exposure. They do not establish that an agent cannot be manipulated, cannot use another connected tool, cannot leak aggregate or quasi-identifier data, or cannot access a different credential.

## 2. Warehouse and data-platform coverage

It should not mean the AI runtime principal itself receives broad metadata privileges. If required metadata is unavailable, report `UNKNOWN`, not “protected.”

**Inference—safe-db-access product shape.** Make the first v2 experience a **plan and proof kit**, not an automated remediator:

1. Detect facts with the audit.
2. Select a vendor/version-specific, reviewed template.
3. Emit parameterized SQL to stdout plus a validation script that proves curated reads work and raw reads fail.
4. Require the human/DBA to execute it.
5. Re-run the audit and attach the before/after evidence.

That satisfies “generate the fix” while keeping the model from inventing executable privilege changes and retaining a credible human gate.

## 7. Explicit non-goals and do-not-build list

**Non-goals**

- Preventing prompt injection or claiming an agent is injection-proof.
- Determining provider-side routing, training, retention, or contractual data handling from local files.
- Compliance certification, legal conclusions, or a universal classification of de-identification.
- Replacing a SIEM, DAM, DSPM, CIEM, secrets manager, endpoint agent, or MCP gateway.
- Guaranteeing that masked, hashed, aggregated, or curated data is non-identifying.

**Do not build**

- A runtime MCP proxy/gateway or agent sandbox. It is a separate operational security product with availability, auth, traffic-inspection, and incident-response obligations.
- LLM-generated finding verdicts or model-scored severity. This destroys the strongest current credibility invariant.
- A homegrown secret scanner fallback when Gitleaks is absent. Keep fail-closed `UNKNOWN`.
- Prompt-redaction-by-default in an audit plugin. Redaction changes user data and belongs in an opt-in runtime path with its own recall/precision testing.
- Direct remediation execution, credential rotation, key generation, or identity provisioning. Those actions require authority, rollback, ownership, and change control the audit cannot infer.
- “One-click compliance.” Standards citations should explain a check’s rationale, not imply certification.
- Live starting of unknown MCP servers during normal audit. Static inspection and explicit delegation are safer defaults.

## 8. Mission and vision

**Mission:** AI Data Security gives data professionals deterministic, cited, read-only evidence about how AI tooling can reach sensitive data and credentials.

**Vision:** Make least-privilege, governed data access for AI agents easy to inspect and prove across common data stacks.
